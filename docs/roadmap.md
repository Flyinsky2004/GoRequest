# 开发路线图

状态：计划，所有里程碑均未宣称完成。此文只规定相对顺序，不估算未经验证的日程。

## 1. 开发顺序与依赖

**MVP → Beta → 1.0-A → 1.0-B → 1.0-C**。

先验证 Native UI 与纯 Go Core 的边界，再完成 Git 友好的基础工作流；先统一请求、变量、结果与测试模型，再扩展多协议与生产力功能。基础阶段可以预埋 Trace 事件和协议接口，但不以“预埋”宣称完整能力。

原对话详细列出 1.0-A/B/C 范围，而 MVP/Beta 阶段交互卡片未保留具体内容。本表根据可读的基础需求补充分期，属于建议，不能冒充原对话已逐项确认的安排。

## 2. MVP：本地 API 与文档闭环

前置验证：MyGo Native UI 在目标平台的 Tree、Tabs、Split、Editor、Markdown、输入法、键盘、文件对话框、大响应展示；验证无网页主窗口。确定文件安全保存的最低实现方式。

交付范围：

- 新建/打开本地项目、全局临时请求、目录树和多标签。
- HTTP 常用方法、URL/Query/Headers、JSON/Text Body、发送/取消、基础超时与 TLS 默认验证。
- 响应 Pretty/Raw、状态/耗时/大小、Headers、基本搜索。
- 项目/环境普通变量，Bearer/Basic 等最小鉴权和显式 Secret 引用；任何已有凭据能力均不得明文落项目。
- 独立请求 YAML、稳定 ID、格式版本、Markdown 编辑/原生预览、本地保存。
- Git 外部编辑可读、文件刷新、未保存内容与磁盘变更冲突保护，无需内置 Git 操作即可协作。

出口：手动建立包含请求与文档的项目，调用本地 HTTP 服务；外部编辑后正确刷新；有编辑冲突时保留双方；打开项目不自动发网。不通过安全保存和原生 UI 验证，不进入“已完成 MVP”。

## 3. Beta：基础工作台稳定化

- 多项目/最近打开、搜索、复制移动、全局与项目转移、主题/字体/快捷键等设置。
- 补齐 XML/Form/multipart/Binary、Cookie 管理、代理、重定向和响应 JSON 树/大内容处理。
- 完整变量来源与继承、系统凭据适配、环境切换和本地历史隔离。
- Markdown 分栏、大纲、附件、链接和稳定请求关联的基础能力。
- Git 状态、Diff、选择性 Commit/Pull/Push；明确 hook 与凭据策略。
- cURL、Postman、OpenAPI/Swagger 的分层导入，便携原生导出及损失报告。
- 单请求可视化断言、JSONPath 提取与简单顺序 Runner，作为正式套件基础。
- Core/GUI 分层检查、桌面内基础运行验证、跨平台文件/输入/权限/取消验证。

出口：两名开发者可 Git 共享项目并保留私密配置；导入失败不破坏文件；取消、大响应与外部更改无数据丢失。Beta 不是多协议或完整自动化能力已交付的声明。

## 4. 1.0-A：自动化基础（P0）

依赖：文件格式、变量、鉴权、结果分类和最小 Core 执行器已稳定。

- Collection Runner + 跨集合 Suite、依赖图、并发隔离、CSV/JSON 数据驱动。
- 断言、提取、声明式前后置、失败策略、受控重试和 JSON/JUnit 报告。
- 桌面内集合 Runner、静态校验、结果分类、程序化自动化调用 Core、取消与报告导出。
- OpenAPI 3.1/3.2 导出、校验、Schema 响应断言、事实来源与有损转换报告；3.2 需单独通过矩阵。
- OAuth2 PKCE、Client Credentials、Device、刷新及 OIDC；TLS/mTLS 配套。
- 安全日志、生产/目标主机策略与格式迁移门槛。

出口：相同项目/凭据/输入下，桌面内保存快照与自动化调用 Core 的登录、查询、更新、校验套件判定一致；报告不泄密；3.1/3.2 及 OAuth 失败路径有验收证据。

## 5. 1.0-B：多协议（P1）

依赖：1.0-A 的执行事件、状态隔离、鉴权与报告；完成流式资源模型评审。

- GraphQL Query/Mutation/Subscription，SDL/Introspection、Explorer、变量、错误模型。
- WebSocket Text/Binary、握手、Ping/Pong、关闭、会话脚本和重放。
- 原生 gRPC 四模式、Reflection/Proto、Metadata/Trailers/Status、Deadline、half-close。
- 三协议的 UI、断言、鉴权、取消、消息限制和脱敏报告一起交付。

出口：每种协议在 Desktop 完成成功、失败、超时、取消与消息边界用例。只增加手工发送界面而无测试自动化，不算该协议里程碑完成。

## 6. 1.0-C：完整开发工作台（P1/P2）

依赖：多协议基础与共享文档模型；Mermaid 先完成技术验证。

- 本地无状态 HTTP Mock、响应场景、模板、延迟、访问记录和套件生命周期。
- 完整 HTTP 时间线、代理/复用/重定向说明、多次采样、分位数与可比报告。
- 文档参数/示例派生、链接检测、离线导出、经验证的 Mermaid 子集与明确兼容范围。
- cURL/Go/Python/JS/TS Snippet；经过选型与兼容测试的规范驱动 SDK。

出口：用一个项目完成 API 定义 → Mock → 调试 → 测试 → 文档 → 规范与代码输出的完整流程。Mermaid 与 SDK 若需缩小范围，必须先更新决策和验收，不能默认为兼容。

## 7. 后续评估与发布原则

后续评估：任意脚本、可执行插件、AsyncAPI、gRPC-Web、有状态 Mock、完整压测、深度 Git 分支/历史与冲突辅助。不得通过“扩展能力”绕开本地安全或主界面路线。

各阶段共享门槛：安全与文件恢复、跨平台、Core/GUI 分离、格式兼容、密钥不入 Git及可取消性。发布前记录实际测试版本、平台、能力矩阵、已知限制和迁移方式，不用规划清单替代实现证据。桌面应用分发需固定版本、完整性校验与可用的离线安装包；发布渠道与签名方式待定。
