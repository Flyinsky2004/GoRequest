## 2. 实现与接线

### 2.1 默认策略只作用于 cURL

- `StageCURLImport` 在 `normalized()` 之前把空 `ConflictPolicy` 设为 `ConflictRenameNewID`；显式 `fail`/`skip`/`overwrite` 原样保留。
- `StageAutoImport` 在归一化前记住调用方是否显式指定策略；仅当格式为 cURL 且未指定时才改为新副本。Postman Collection、Postman Environment、Portable Bundle 仍默认 `ConflictFail`，没有改成全局强制覆盖。
- 桌面 `OpenImportModal` 通过 `defaultConflictPolicyIdx` 设置默认：cURL 为 `1`（分配新 ID 副本），其他来源为 `0`（冲突时阻止）。从「+」菜单的「从 cURL 导入…」和项目菜单进入时均走该入口。

### 2.2 安全独立 ID 与文件名

- `resolveEntityCollision` 的 rename 序列改为 `base` → `base-copy` → `base-copy-2` → `base-copy-3`…，连续四次导入得到四个不同 ID/路径。
- `StageCURLImport` 在分配前调用 `diskRequestIDs` 扫描 `collections/**/*.request.yaml`，解析文件内 `id`（解析失败时保守使用文件名 stem）并播种 `usedIDs`。因此：
  - 磁盘已有文件但 `p.Requests` 未刷新时，同目录路径冲突由 `Store.Exists` 拦截；
  - 不同目录但磁盘已有同 ID 时，ID 仍被视为占用并分配新副本，避免重开项目后同 ID 互相覆盖。
- `existsPath` 对存在但不可读（超限、符号链接等）的目标也视为已占用，rename 不会复用该路径。
- 原请求文件只读不写；副本各自独立写入。

### 2.3 陈旧计划确认

- `ImportPlan.Apply` 在任何写盘前执行 `validateRequestIDUniqueness`：若计划中的请求 ID 已被另一路径使用，返回 `ErrRequestIDConflict`，不产生部分写入。该检查同时覆盖内存与磁盘。
- `ChangeSet` 原有保护继续生效：create 目标已存在、update/delete/move 基线摘要不匹配时在 prepare 阶段拒绝，不会写坏文件。
- 桌面 `ConfirmAndApplyImport` 在 rename 策略下遇到 `ConflictError`/`ErrRequestIDConflict` 时：
  1. 不应用旧计划；
  2. 基于当前磁盘/内存重新生成预览；
  3. 显示「目标在预览后发生变化，已重新生成预览；请检查后再次确认。」（英文对应文案）；
  4. 等待用户再次确认。
- 显式 overwrite/fail/skip 不自动重规划：overwrite 的基线不匹配直接报错，fail 继续阻止，skip 继续不写入。

### 2.4 保存/重开/撤销/删除

- 每个副本使用独立文件与 ID；保存后 `OpenProject` 可恢复全部副本。
- 桌面「撤销上次导入」只回滚最近一次 receipt；core 测试验证撤销最后一个副本后其余副本与共享 secret 槽位仍在。
- 删除一个副本文件并重载项目不影响其他副本；再次导入会获得新的独立副本。
- ID 由现有磁盘/内存状态确定性分配，已存在副本的 ID 不因后续导入改变。

### 2.5 UI 补丁（交 U22）

`docs/task-results/U23-import_export_ui.patch` 仅一行：模态内切换来源时调用 `defaultConflictPolicyIdx(st.ImportSourceKind)`，使从 Postman 切到 cURL 也得到新副本默认策略。补丁采用零上下文格式，避免补丁自身的上下文行触发 `git diff --check` 的 space-before-tab 检查。该文件归 U22，本卡未修改；`git apply --check` 已验证可应用。cURL 专用菜单入口的默认策略已在本卡 `import_export.go` 真实接线，不依赖该补丁。
