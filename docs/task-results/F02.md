## 根因和实现选择

能力分三层，彼此不复制逻辑；**没有新建 Runner**。

1. `internal/core`（纯 Go，无 GUI 依赖）
   - `graphql_schema.go`：`GraphQLSchemaModel` 从 SDL 构建类型/字段/参数/枚举/描述/弃用信息；`ValidateDocument` 先解析文档、再对已加载的 `ast.Schema` 做完整语义校验，返回带 `Line/Column` 的诊断。解析失败时仍返回 operation 清单，下拉框不会因选错而清空。
   - `graphql_introspection.go`：固定 introspection 查询文档、响应解析（先校验 `MaxGraphQLIntrospectionBytes` 再截断）、`GraphQLIntrospectionRef` 保留目标并丢弃响应体。
   - `graphql.go`：把 `AnalyzeGraphQL` 拆成“拒绝 subscription 的 HTTP 入口”和“不限制类型的 `AnalyzeGraphQLDocument`”，operation 选择改为显式 `selectGraphQLOperation`（多 operation 未指定名字 → 报错并列出名字，**不随机取第一个**）。
   - schema 引用存 `Extensions["graphqlSchema"]`，`Digest` 是用户校验过的 SDL 原始字节 SHA-256；文件改动后 digest 变化可见，不静默沿用旧校验结果。
   - 所有上限集中为常量（`MaxGraphQLSchemaBytes`、`MaxGraphQLSchemaTokens`、`MaxGraphQLSchemaTypes`、`MaxGraphQLSchemaFieldsPerType`、`MaxGraphQLSchemaArgsPerField`、`MaxGraphQLSchemaEnumValues`、`MaxGraphQLSchemaDescriptionBytes`、`MaxGraphQLIntrospectionBytes`）。解析走 `parser.ParseSchemasWithLimit(MaxGraphQLSchemaTokens, ...)`。

2. `internal/websocket` + `internal/protocolrun`
   - `subscription.go` 实现 `graphql-transport-ws`：`connection_init`→`connection_ack`（`AckTimeout` 内未到即失败关闭）、`connection_error` 视为 init 拒绝且不发送 `subscribe`、每 operation 唯一 `id`、`next` 进入有界队列、`error` 记录协议错误并终止该 operation、`complete` 双向、`ping`/`pong`、未知/错配 id 只记协议错误不影响其他 operation。**不静默重连**；旧版同名 `graphql-ws` 子协议明确拒绝。
   - init 认证材料只放 `InitPayload`；`InitPayloadSensitive=true` 时时间线按敏感值脱敏，同时把值注册进 redactor。
   - `websocket.Options` 新增 `FrameHandler`/`InboundSensitive`/`CookieJar`，`Session` 新增 `Done()`、`SendTextSeq`/`SendBinarySeq`。这些是**可选**字段：不设置时手动会话行为不变（`FrameHandler` 为 nil 不触发，`InboundSensitive` 为 false 时保留原文，`CookieJar` 为 nil 不发送 cookie）。
   - `protocolrun` 实现 connect→send(text/binary)→await/assert→close：显式接收游标（`current`/`start`）、逐步超时、未匹配消息 `SkippedFact{Seq, Bytes, Retained}`、单帧/累计字节/保留条数上限、整次 deadline。`Run` 总是返回 `Result`，失败即中止并保留 `CloseFacts`，**不重连不重试**。协议结束事实（`CloseCode`/`CloseReason`、每步 `Direction`/`CursorBefore`/`CursorAfter`/`SentSeq`/`ReceivedSeq`/`ReceivedBytes`）独立保留，**不扁平化为 HTTP 状态**。
   - 计划文件只保存模板（`{{...}}`），运行时才用**当前**环境与 Secrets 解析；重放重新读盘、重新解析，绝不复用历史鉴权值。预览有界且脱敏，二进制预览掩码。

3. `internal/desktop`（原生 UI）
   - GraphQL 工作区扩为五分区（Document / Variables / Schema / Headers / Auth），徽标下标随分区数组同步（`badges[3]`）。
   - Schema Explorer：类型/字段/参数/描述/弃用 + 搜索过滤 + 点选字段插入片段。**没有**扩展全局编辑器，也没有 schema 驱动的自动补全。
   - Introspection 仅显式按钮触发、可取消、先预览后保存；打开项目或编辑文档从不自动抓取。
   - 订阅时间线：数据 / 错误 / 传输关闭三态可区分，显式取消；状态回写用 `weak.Pointer[App]` + generation 守卫，窗口销毁后不写。
   - WebSocket Script 分区：选计划文件 → 校验（零网络）→ 运行/取消 → 逐步事实与 close 事实。与手动 Messages 面板是**两个独立分区**，不共用运行状态。
   - 二进制文件发送：原生文件选择 + 大小上限校验。

**计划引用（供 Runner 定位计划）**：`internal/protocolrun/planref.go` 把计划文件与请求绑定为 `Extensions["wsPlan"] = {path, digest}`（镜像 `graphqlSchema`：只存项目相对路径 + 已审阅字节的 SHA-256，不复制计划正文、不含解析后的凭据）。`internal/desktop/websocket_plan.go` 在选择项目内计划文件时写入该引用并标脏；打开 tab 时按引用本地重载（零网络），文件改动会显示 digest 变化提示。这样 F01 端口即使 `ProtocolRequest` 不带路径也能靠请求扩展取到计划。

**为什么不在这里写 Runner 适配器**：本 worktree 不含 F01 端口代码，`grep -rn "ProtocolExecutor" internal/` 返回 0 处匹配，适配器在本分支无法编译。因此适配器以接线文档形式交付：`docs/task-results/F02-integration.patch`。但该 patch 里的适配器源码（`internal/protocolrun/runneradapter/adapter.go`）**已按真实端口签名做过验证**：临时拷入 F01 的 `port.go` 并加 `Variables` 字段后 `go build`/`go vet` 均零错误，验证用临时文件在提交前精确撤回、未进入本分支。patch 仍是接线文档而非可直接 `git apply` 的统一 diff，因为端口代码不在本分支。

**GraphQL 走 Runner 的额外前提**：`core.BuildTrackedPlanWithOptions` 在 `PlanOptions.AllowGraphQL == false` 时直接返回 `configErrorf("GraphQL requests are not supported by this execution path yet")`，而 F01 的 `runner_snapshot.go` 未设置该字段。缺它时 GraphQL 步骤在计划构建阶段就失败，**根本到不了端口**；WebSocket 步骤不受此限制，会以 `Method == "WS"` 正常进入端口。这一点已写入契约第 9 节和接线文档。
